# التحقق من نصاب 24 ساعة وحفظ مسودات مراجعة مستقلة — TPS

**الحالة:** أداة تشغيل محلية تجريبية. اختبارات CI اصطناعية ولا تثبت تحقيق 24 ساعة في بيانات الكلية. لا يتغير أي سيناريو أصلي أو معتمد باستخدام هذه الأداة.

## قواعد إلزامية

- لا تستخدم GitHub Actions أو السحابة للوصول إلى بيانات المدربين أو المتدربين التشغيلية. التشغيل على Windows المحلي فقط، وبقاعدة `tps_operational_local` على `127.0.0.1`.
- الأداة تثبت هدف **24 ساعة نصاب محتسب** للمدربين ذوي الرمز `5` و`6`، ولا تعتبره 24 ساعة زمنية على الساعة. تقبل فقط نتيجة Timefold ذات `hard=0` مع تغطية مقررات الأولوية وعدم وجود موانع غير العجز الظاهر.
- يجب أن يثبت فحص أسماء المدربين أن الرمزين `5` و`6` يعودان إلى **محمد وفهد**. لا تفترض ترتيب الاسمين. يجب أن تبقى الحدود الأساسية وأي استثناءات رسمية كما هي؛ إذا كانت السعة المصرح بها أقل من 24، تتوقف الأداة ولا ترفعها اصطناعيًا.
- يجب أن تتضمن اللقطة ستة مدربين برموز `1..6`، والسيناريوهات الثلاثة المطلوب فحصها جميعًا من الحالة `DRAFT` مع حل `COMPLETED`، وللقسم والفصل نفسيهما.
- مدرب `1` يبقى عند شعبتين، ومدرب `2` عند 12 ساعة محتسبة، ومدربا `5/6` لا يسند لهما عملي بحت؛ المقررات المختلطة المغطاة لهما، ومقررات القسم ذات الأولوية لا تُترك بعجز.
- أي عجز آخر يبقى ظاهرًا بصراحة ولا يتحول إلى جدول مصطنع.
- ملف التحضير يحوي لقطات داخلية حساسة نسبيًا، ويُحفظ تحت `private-data/load24/` المتجاهَل من Git. **لا ترفعه إلى مستودع عام أو ترسله في المحادثة.** السجل المطبوع يعرض مفاتيح السيناريوهات والأعداد فقط.

## 1 — تجهيز المصدر دون فقد البيانات

من PowerShell على جهازك داخل `H:\tps_system`:

```powershell
cd H:\tps_system
git status --short --branch
git fetch origin "refs/heads/feat/load24-guarded-review-20261108:refs/remotes/origin/feat/load24-guarded-review-20261108"
```

توقف إذا كانت هناك تغييرات محلية غير محفوظة. **لا تستخدم `reset --hard` أو `clean` أو `force-push`.** بعد التأكد من أن فرعك الحالي سلف مباشر للفرع الجديد وأنه لا توجد تغييرات متعارضة، يتم التحديث دون إعادة كتابة التاريخ:

```powershell
git merge --ff-only origin/feat/load24-guarded-review-20261108
npm run build
node --check scripts/load24-operational.mjs
```

لا حاجة إلى تعديل الجداول التشغيلية أو تشغيل الترحيلات لهذا التغيير البرمجي. إذا كان مطلوبًا `npm ci` على Windows، أوقف خدمة TPS المعروفة إيقافًا سليمًا أولًا طبقًا لدليل الترقية، **ولا توقف PostgreSQL**.

## 2 — استعراض السيناريوهات الموجودة (قراءة فقط)

```powershell
$DepartmentId = "<UUID_OF_DEPARTMENT>"
node scripts/load24-operational.mjs list --department-id $DepartmentId
```

اختر **معرّفات الثلاثة فقط** التي تحمل المفاتيح `BASE_157` و`CAP_100_50_40` و`CAP_120_40_ECO50`. لا تستخدم السيناريوهات المرجعية أو المسودات الأخرى. الأداة تتحقق من العدد والتمييز والحالة والفصل قبل أي حساب.

## 2أ — تشخيص حدود النصاب عند التوقف (قراءة فقط)

إذا ظهرت الرسالة `LOAD24_GATE: Trainer 6 has no approved capacity for 24 credited hours`، فلا ترفع `maxLoad` أو تضع استثناءً داخل لقطة السيناريو تلقائيًا.

```powershell
node scripts/load24-operational.mjs diagnose --department-id $DepartmentId --scenario-ids $ScenarioIds
```

يعرض التشخيص لكل مدرب في كل سيناريو: `scenarioBaseLimit` والزيادة المعتمدة داخل اللقطة `scenarioApprovedException` ومجموعهما `scenarioEffectiveLimit` والساعات المسندة حاليًا `currentCredited` والفجوة إلى 24 `missingCapacityTo24`، بالإضافة إلى `masterBaseLimit` و`masterApprovedException` من قاعدة البيانات الحالية للفصل. `snapshotDiffersFromMaster=true` يعني أن بيانات المدرب أو الاستثناء المعتمد تغيرت بعد حفظ لقطة السيناريو، ولا يجوز تحديث اللقطة التاريخية بصمت. التشخيص لا يكتب أي شيء في PostgreSQL.

- إذا كان `scenarioEffectiveLimit < 24` و`masterEffectiveLimit >= 24`، فقد يكون السيناريو القديم لا يعكس حدودًا أو استثناءات معتمدة حاليًا؛ يجب إنشاء سيناريو جديد من البيانات المصرّح بها مع الاحتفاظ بالأصل.
- إذا كان الاثنان أقل من 24، لا تصف النقص بأنه خلل Timefold. يلزم قرار إداري مستقل وفق سياسة الكلية بشأن إمكانية زيادة النصاب أو استثناء رسمي للفصل؛ وإلا تبقى نتيجة أقل من 24.
- لا تنشر أسماء المدربين أو بياناتهم أو المخرجات التفصيلية في GitHub. عند مشاركة التشخيص، يكفي رمز المدرب والأرقام اللازمة مع حجب الاسم.

## 3 — تجربة Timefold وحفظ إثبات خاص (قراءة فقط)

```powershell
$ScenarioIds = "<UUID_1>,<UUID_2>,<UUID_3>"
node scripts/load24-operational.mjs prepare --department-id $DepartmentId --scenario-ids $ScenarioIds
```

تنفذ الأداة 15 ثانية ثم 30 ثانية إذا لم ينجح التحقق، باستخدام 24 مرشحًا لكل مدرب. **إذا لم تتحقق كل الشروط، تتوقف دون أي حفظ في PostgreSQL.** إذا نجحت الثلاثة، تُنشئ ملفًا خاصًا باسم `private-data/load24/load24-...json` يحوي لقطات المصدر والتوزيع المقترح وبصماتها ودرجات Timefold وملخصًا مختصرًا.

## 4 — الحفظ الاختياري بعد مراجعة النتائج والنسخة الاحتياطية

هذه مرحلة مستقلة متعمدة. يجب قبلها إنشاء نسخة احتياطية تشغيلية مشفرة باستخدام إجراءات TPS الحالية، والتحقق من سلامتها واستعادتها اختباريًا. لا تتعامل مع مجرد وجود ملف `.tpsbak` بوصفه إثباتًا للاستعادة.

```powershell
$StageFile = "<FULL_PATH_UNDER_private-data/load24>"
$BackupFile = "<FULL_PATH_UNDER_private-data/backups_TO_VERIFIED_tpsbak>"
$ActorId = "<UUID_OF_AUTHORIZED_LOCAL_USER>"
$secure = Read-Host "TPS backup passphrase" -AsSecureString
$ptr = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($secure)
try {
  $env:TPS_BACKUP_PASSPHRASE = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($ptr)
  node scripts/load24-operational.mjs commit --department-id $DepartmentId --stage-file $StageFile --actor-id $ActorId --backup-file $BackupFile --confirm COMMIT_THREE_REVIEW_DRAFTS
} finally {
  Remove-Item Env:TPS_BACKUP_PASSPHRASE -ErrorAction SilentlyContinue
  [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($ptr)
}
```

قبل أي كتابة، تُفحص هوية وصلاحية المشغّل، وسلامة النسخة الاحتياطية، وثبات بصمات اللقطات الأصلية وإصداراتها، وحالة `DRAFT` و`COMPLETED`، وعدم إنشاء مسودة مراجعة أخرى بذات الاسم والمصدر. تتم **إضافة ثلاث مسودات جديدة مرتبطة بالسيناريوهات الأصلية في معاملة PostgreSQL واحدة** مع سجلات تدقيق وتاريخ حل؛ إذا فشل أي شرط تُلغى المعاملة بالكامل. لن تتغير السيناريوهات الأصلية، ولن يتم إجراء اعتماد أو نشر إلى رايات.

## 5 — التقارير بعد حفظ مسودات المراجعة

تُنشأ تقارير المدربين والمتدربين والقاعات من **اللقطات المحفوظة** في كل مسودة جديدة عبر واجهة TPS أو واجهات التنزيل المعتمدة، لكل نوع بصيغتي Excel وPDF. لا تصدر تقارير نهائية من ملف التحضير وحده ولا تعتبر سيناريوهات المراجعة معتمدة. راجع العجز والتنبيهات وتوزيع الساعات قبل طلب الاعتماد الإداري.

## حالات التوقف المتعمد

- غياب أحد المدربين أو خطأ ربط الرمز بالاسم.
- المستهدف 24 يتجاوز الحد الأساسي المصرح به، أو توجد قيود زمنية/غرف تمنع الجدولة.
- عدم تغطية مقرر أولوية، أو وجود تعارض Hard، أو اختلاف عضوية المتدربين أو إجمالي الطلب.
- اختلاف السيناريو الأصلي بعد `prepare`، أو محاولة حفظ مسودة مكررة، أو مرور أكثر من 48 ساعة على التحضير.
- عدم وجود نسخة احتياطية مشفرة قابلة للتحقق، أو غياب مستخدم ذي صلاحية صريحة، أو الاتصال بقاعدة بيانات ليست محلية.

**الحد الحالي:** كود الأداة واختبارات المكونات على GitHub لا يثبتان نجاح هذه الإجراءات على جهاز الكلية. لا بد من تشغيل المرحلتين الأولى والثانية والثالثة محليًا والتحقق من النتائج الفعلية قبل التفكير في الحفظ.
